# 토스페이먼츠 라이브키 발급

## 문서 목적

이 문서는 PASSV 이용권(memberships) 결제에 쓰는 토스페이먼츠 **라이브(실연동) 키**를 발급받아 운영 변수에 반영하는 절차를 정리한다.

토스페이먼츠는 로그인만 한다고 라이브 키가 바로 나오지 않는다. **가맹점 계약 심사가 완료돼야** 라이브 키가 열린다. 테스트 키는 로그인 직후부터 쓸 수 있고, 라이브 키는 심사 승인 후 상점관리자에서 모드를 전환해야 보인다.

이 문서에서 끝내야 하는 일은 아래 4가지다.

1. 상점관리자에서 실서비스 계약을 신청하고 심사를 통과한다.
2. 라이브 모드로 전환해 라이브 클라이언트 키와 시크릿 키를 확인한다.
3. 확인한 값을 PASSV 백엔드 운영 변수에 넣는다.
4. 이용권 결제 흐름에서 라이브 결제가 정상 동작하는지 확인한다.

## 먼저 알아둘 값

| 항목 | 값 |
| --- | --- |
| 상점관리자 | `https://dashboard.tosspayments.com` |
| API 호출 기준 URL | `https://api.tosspayments.com/v1` (테스트·라이브 공통) |
| 백엔드 변수 1 | `TOSS_CLIENT_KEY` |
| 백엔드 변수 2 | `TOSS_SECRET_KEY` |
| 백엔드 변수 3 | `TOSS_WEBHOOK_SECRET` |
| 테스트 키 접두어 | 클라이언트 `test_ck_...` / 시크릿 `test_sk_...` |
| 라이브 키 접두어 | 클라이언트 `live_ck_...` / 시크릿 `live_sk_...` |
| PASSV 결제 연동 방식 | 빌링키(자동결제) 기반 이용권 정기결제 |

중요한 점은 아래 4개다.

1. API 호출 URL은 테스트·라이브가 같다. **환경을 가르는 것은 키 접두어**(`test_` / `live_`)다. 그래서 URL이 아니라 키를 라이브로 바꾸는 것이 핵심이다.
2. **시크릿 키는 백엔드에서만 사용**한다. 프론트·저장소·로그에 절대 노출하지 않는다.
3. 라이브 키는 계약 심사 승인 전에는 상점관리자에 표시되지 않는다. 키가 안 보이면 설정 문제가 아니라 심사 단계 문제다.
4. 테스트 키와 라이브 키를 섞어 쓰면 인증(`UNAUTHORIZED_KEY` 계열) 오류가 난다. 클라이언트·시크릿 키는 **같은 환경끼리** 맞춰서 넣는다.

## 초안 상태

- 이 문서는 2026-07-15 기준 초안이다.
- 상점관리자 화면 문구·버튼 위치 캡처는 아직 붙이지 않았다.
- 토스페이먼츠 상점관리자 화면은 이후 바뀔 수 있으므로, 최종 적용 직전 한 번 더 확인한다.

## 전체 순서

1. 상점관리자에 로그인하고 계약 상태 확인하기
2. 실서비스 계약 신청하기
3. 심사 서류 제출하기
4. 심사 승인 확인하기
5. 라이브 모드로 전환해 라이브 키 확인하기
6. 웹훅 시크릿 확인하기
7. PASSV 운영 변수에 반영하기
8. 이용권 결제 흐름에서 마지막 확인하기

## 1. 상점관리자에 로그인하고 계약 상태 확인하기

### 작업 순서

1. `https://dashboard.tosspayments.com`에 로그인한다.
2. 상단 모드 표시가 `테스트`인지 `라이브(실연동)`인지 확인한다.
3. 계약 메뉴에서 현재 상점의 계약 상태를 확인한다.

### 설명

- 로그인 직후 기본은 테스트 모드다. 이 상태에서는 `test_` 접두어 키만 보인다.
- 계약이 아직 없거나 `심사 중`이면 라이브 키는 잠겨 있다.
- 계약이 `완료/승인` 상태여야 라이브 모드 전환이 가능하다.

## 2. 실서비스 계약 신청하기

### 작업 순서

1. 상점관리자의 계약 관리(또는 `가맹점 신청/계약하기`) 메뉴로 이동한다.
2. 결제를 붙일 서비스(도메인·서비스명)에 대한 실서비스 계약을 신청한다.
3. 신청 대상 상점이 PASSV 운영 서비스와 맞는지 확인한다.

### 설명

- 라이브 키는 상점(서비스) 단위로 발급된다. 그래서 계약도 실제 결제를 붙일 서비스 기준으로 신청한다.
- 이미 신청한 계약이 있으면 새로 만들지 말고 그 계약의 심사 진행 상태를 따라간다.

## 3. 심사 서류 제출하기

### 작업 순서

1. 계약 신청 화면에서 요청하는 서류를 제출한다.
2. 최소한 아래 항목을 준비한다.

```text
- 사업자등록증
- 정산 받을 대표 계좌(통장 사본)
- 서비스 URL / 앱 정보, 판매 상품·서비스 소개
- 대표자/담당자 정보
- (업종에 따라) 통신판매업 신고증 등
```

3. 제출 후 반려 항목이 없는지 확인한다.

### 설명

- 서류가 누락되면 심사가 반려되거나 지연된다.
- 통신판매업 신고 등 업종별 추가 서류는 판매하는 상품·서비스 종류에 따라 달라진다.

## 4. 심사 승인 확인하기

### 작업 순서

1. 계약 상태가 `심사 중`에서 `완료/승인`으로 바뀌었는지 확인한다.
2. 승인 안내(메일·알림)를 확인한다.

### 설명

- 심사는 보통 영업일 며칠이 걸린다.
- 승인 전에는 5단계 라이브 모드 전환이 열리지 않는다. 승인될 때까지는 테스트 키로 개발·검증을 이어간다.

## 5. 라이브 모드로 전환해 라이브 키 확인하기

### 작업 순서

1. 상점관리자 상단에서 모드를 `라이브(실연동)`로 전환한다.
2. `개발자센터` 또는 `API 키` 메뉴로 이동한다.
3. 아래 두 값을 확인한다.

```text
클라이언트 키: live_ck_...
시크릿 키:     live_sk_...
```

4. 시크릿 키는 안전하게 복사해 둔다.

### 설명

- 라이브 모드에서 보이는 키가 실제 결제에 쓰이는 키다.
- 클라이언트 키는 결제창/빌링 인증 위젯에서 쓰고, 시크릿 키는 백엔드에서 결제 승인·빌링키 발급 API 호출에 쓴다.
- 시크릿 키는 다시 확인이 어려울 수 있으니, 복사한 값을 바로 시크릿 저장소에 넣는다.

## 6. 웹훅 시크릿 확인하기

### 작업 순서

1. 상점관리자에서 웹훅(Webhook) 설정 화면으로 이동한다.
2. PASSV 결제 웹훅 수신 URL이 등록돼 있는지 확인한다.
3. 웹훅 서명 검증에 쓰는 시크릿 값을 확인한다.

### 설명

- PASSV 백엔드는 `TOSS_WEBHOOK_SECRET`으로 토스 웹훅 서명을 검증한다.
- 이 값이 설정돼 있으면 서명 불일치 요청은 `401`로 거부되고, 미설정이면 통과시키되 경고를 남긴다(현재 백엔드 동작 기준).
- 운영에서는 웹훅 시크릿을 반드시 설정해, 위조된 결제 알림이 통과하지 않게 한다.

## 7. PASSV 운영 변수에 반영하기

### 이 단계에서 기억할 규칙

상점관리자에서 확인한 라이브 값을 아래처럼 넣는다.

| 위치 | 변수명 | 넣는 값 |
| --- | --- | --- |
| 백엔드 운영 변수 | `TOSS_CLIENT_KEY` | 라이브 클라이언트 키 `live_ck_...` |
| 백엔드 운영 변수 | `TOSS_SECRET_KEY` | 라이브 시크릿 키 `live_sk_...` |
| 백엔드 운영 변수 | `TOSS_WEBHOOK_SECRET` | 토스 웹훅 서명 검증 시크릿 |

### PASSV 코드 기준으로 보면

| 구분 | 파일 | 의미 |
| --- | --- | --- |
| 변수 정의 | `services/sens-api/config.py` | `TOSS_CLIENT_KEY`, `TOSS_SECRET_KEY`, `TOSS_WEBHOOK_SECRET` 선언 |
| 예시 변수 | `services/sens-api/.env.example` | `TOSS_CLIENT_KEY`, `TOSS_SECRET_KEY` 자리 |
| 결제 클라이언트 | `services/sens-api/contexts/payments/application/services.py` | `TossPaymentsService`(기준 URL `https://api.tosspayments.com/v1`, 시크릿 키로 Basic 인증) |
| 이용권 정기결제 | `services/sens-api/contexts/memberships/application/services.py` | 빌링키 발급·정기결제 처리 |

### 설명

- 운영 시크릿은 평문으로 코드·저장소에 넣지 않는다. 시크릿 반영은 [Infisical 시크릿 반영과 권한 변경 절차](../../07. 시크릿-권한 작업/Infisical 시크릿 반영과 권한 변경 절차/index.md)를 따른다.
- 시크릿 키는 백엔드 API 호출(빌링키 발급, 결제 승인)에서만 쓴다. 프론트에는 시크릿 키를 넣지 않는다.
- 테스트 키와 라이브 키를 한 환경에 섞지 않는다. DEV/PROD 환경별로 키 세트를 분리해 관리한다.

## 8. 이용권 결제 흐름에서 마지막 확인하기

### 작업 순서

1. 운영 변수 반영 후 백엔드를 재기동한다.
2. 이용권 결제(빌링키 발급 → 정기결제) 흐름을 실제로 한 번 태운다.
3. 상점관리자 라이브 모드의 결제 내역에서 해당 건이 잡히는지 확인한다.
4. 실패 시 사용한 키의 접두어(`test_`/`live_`)와 클라이언트·시크릿 키의 환경 일치를 먼저 확인한다.

### 설명

- 라이브 결제는 실제 청구가 발생한다. 검증 시 최소 금액 또는 사전에 합의된 방법으로 진행한다.
- 인증 오류가 나면 대부분 키 환경 불일치나 시크릿 키 오탈자다.
- 웹훅이 안 잡히면 웹훅 URL 등록과 `TOSS_WEBHOOK_SECRET` 값을 확인한다.

## 초보 운영개발자용 최종 체크리스트

1. 상점관리자에서 실서비스 계약을 신청했다.
2. 심사 서류(사업자등록증·정산계좌 등)를 제출했다.
3. 계약 상태가 `완료/승인`으로 바뀐 것을 확인했다.
4. 라이브 모드로 전환해 `live_ck_...`, `live_sk_...`를 확인했다.
5. 웹훅 URL 등록과 웹훅 시크릿을 확인했다.
6. `TOSS_CLIENT_KEY`에 라이브 클라이언트 키를 넣었다.
7. `TOSS_SECRET_KEY`에 라이브 시크릿 키를 넣었다(백엔드 전용).
8. `TOSS_WEBHOOK_SECRET`에 웹훅 시크릿을 넣었다.
9. 시크릿은 Infisical 절차로 반영하고 평문 노출을 남기지 않았다.
10. 이용권 결제 흐름을 태워 라이브 결제 내역이 잡히는 것을 확인했다.
