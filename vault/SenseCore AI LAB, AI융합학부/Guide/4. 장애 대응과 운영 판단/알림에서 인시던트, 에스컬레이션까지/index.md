# 알림에서 인시던트, 에스컬레이션까지

이 문서는 알림 하나가 떴을 때, 그것을 어떻게 인시던트로 다루고 언제 사람을 더 부르는지(에스컬레이션) 흐름과 기준을 정리한다.

## 흐름 한눈에

```
알림 발생 → Alerta 등록 → 분류(triage) → 대응 → 해소(resolve) → 회고
                              │
                       심각도/영향 판단
                              │
                    필요 시 에스컬레이션
```

## 심각도(severity) 정의

플랫폼 알림은 4단계 라벨을 쓴다(`platform-alert-rules.yaml` 등).

| severity | 뜻 | 예 | 1차 기대 반응 |
| --- | --- | --- | --- |
| critical | 사용자 영향 큼/가용성 위협 | 배포 가용 0, MySQL Ready 0, fast burn, 엔드포인트 다운 | 즉시 대응 |
| major | 일부 기능·품질 저하 | 5xx 비율 높음, OOMKilled, PVC 잔여 부족 | 빠른 확인 |
| warning | 잠재 위험/추세 악화 | p95 상승, CPU throttling, slow burn, 인증서 임박 | 당일 내 조사 |
| minor | 경미/정보성 | — | 모니터링 |

## 인시던트 다루는 순서

1. **확인(triage)**: Discord 알림 → Alerta에서 같은 서비스/alertname 묶음 확인. 진짜 영향인지, 노이즈인지 판단.
2. **범위 파악**: 전체인가 특정 서비스인가, 언제부터인가, 인프라인가 앱인가. → [모니터링·알림 아키텍처 가이드](../../3. 데이터, 관측, 보안/모니터링·알림 아키텍처 가이드/index.md)의 메트릭→로그→트레이스 순서.
3. **대응**: [장애 대응 의사결정 가이드](../장애 대응 의사결정 가이드/index.md)로 롤백/핫픽스/대기 결정. 서비스별 1차 절차는 각 서비스 가이드의 `3. 운영 절차`.
4. **해소·회고**: Alerta에서 close, 원인·재발 방지를 짧게 기록.

## 에스컬레이션 기준 (TODO: 확정 필요)

> 아래는 제안값이다. 온콜 로테이션과 채널은 팀에서 확정해야 한다.

- **온콜 채널(제안)**: 현행 운영 Discord 채널을 1차 알림으로 사용.
- **에스컬레이션 트리거(제안)**:
  - critical이 15분 내 ack되지 않으면 담당자 멘션 → 30분 내 미해소 시 책임자 호출.
  - 다중 서비스 동시 critical(플랫폼 광역 장애)은 즉시 책임자 호출.
- **확정 필요 항목**: 온콜 로테이션 표, 멘션 대상, 2차/3차 연락처, 점검창 합의 방식.
